# Sony α7R VI 1.02: acquired firmware and XR2 decryption boundary

Checked locally on 2026-10-21 against the [Sony US release](https://www.sony.com/electronics/support/e-mount-body-ilce-7-series/ilce-7rm6/software/00413269), [Sony Japan release](https://support.sony.jp/electronics/support/e-mount-body-ilce-7-series/ilce-7rm6/software/00413256), the official [ILCE-7RM6 1.02 OSS listing](https://oss.sony.net/Products/Linux/DI/ILCE-7RM6_Ver102.html), and [Sony's XR2 model description](https://www.sony.jp/ichigan/products/ILCE-7RM6/feature_1.html). The US official download control supplied `BODYDATA.DAT`. The isolated original is `F:\New project\sony-a7r6-release-verify-20261021\BODYDATA.DAT` (338,327,032 bytes, SHA-256 `831fa09a2839840cd0066fec2cc7ad68c0bb574ecd28ecd4305a64690eb454e9`). The original was not executed or installed. The public repository contains neither its encrypted bytes nor decrypted Sony files.

## Measured result

- The UFU outer container has `DATV(4)`, `PROV(4)`, `UDID(44)`, `FDAT(338326928)`, and `DEND(4)`. It has no trailing data. Its stored and calculated CRC32 both equal `0x6fcf68eb`.
- FDAT starts at file offset `0x5c`, has length `0x142a7590`, and leaves `0x190` bytes after 330,397 whole 1024-byte blocks. The older `0x110`-byte-tail layout does not align. This length geometry matches the locally studied A7 V/XR2 sample, but does not establish the same cipher or key.
- The older common AES first stage did not produce `UDTRFIRM`. Eighteen publicly discussed CXD90057 keys, 270 bounded first-block transformations, and 450 aligned tail-IV variants produced **zero** Sony block-checksum or magic hits. These are negative tests for specified hypotheses, not a proof that the FDAT cannot be decrypted.
- An independent 16-byte-block comparison of the first 512 FDAT bytes found 7 distinct blocks in the old A7R V 4.00 sample (one ciphertext block repeated 26 times), but 32/32 distinct blocks in both A7 V 2.00 and A7R VI 1.02. This is consistent with loss of the old ECB-visible header pattern; different plaintext structure remains another explanation. The reproducible result and script are `F:\New project\sony-xr2-method-20261021\first512-block-compare.json` and `compare-fdat-first512.py`.
- Current `devkit.cli inspect` reports `sony-dat`, `extractable=false` and an unsupported XR2/unknown encryption geometry. It correctly does not extract components or claim an A7R VI emulator profile. The separate structural probe checks the full outer CRC; the generic top-level CLI summary does not claim that check.

The official OSS bundle includes `cemmc-init`, `cryptoram` and a Linux kernel. `cemmc-init` sets an **eMMC XTS** key via an OP-TEE KEYSET pseudo-TA; `cryptoram` provides caller-keyed crypto interfaces. A search of the supplied sources found no BODYDATA/FDAT updater implementation or secure-world TA body. The eMMC key-setting path is not evidence of the FDAT update-package key. Source hashes, exact file locations and search limits are recorded in the isolated `oss-xr2-findings.md`.

## Next decryption method, with explicit acceptance gates

The [fwtool CXD90057 research](https://github.com/ma1co/fwtool.py/pull/52) and its [key-discovery discussion](https://github.com/ma1co/fwtool.py/issues/39) explain why an older BIONZ XR key cannot be assumed to work on XR2: the prior derivation was recovered from device-side updater code and hardware-dependent inputs; the author reported no XR2 device sample. The locally available A7R V updater provides **old-generation comparison anchors**, not XR2 answers. Its `crypter.elf` imports `libcryptfileinputupdaterapi.so` and `libupdatertalk.so`; the former exposes `CryptFileInputUpdaterManager::searchFDAT` and `verifyFile` and calls `DecryptorModule::decrypt` from `libupdatercorecommon.so`. Exact ELF hashes, symbols and virtual addresses are in `F:\New project\sony-xr2-method-20261021\XR2-DECRYPTION-METHOD-AUDIT.md`; its `static-updater-index.ps1` can index a future authorized, read-only XR2 device dump against these old-model anchors.

The next useful input is a **read-only XR2 device-side updater and associated libraries/secure-world interface trace**. Search for the old symbol/file anchors, then follow the actual XR2 FDAT entrypoint and identify how it consumes the `0x190`-byte tail, chooses the cipher, obtains its key or handle, and invokes any TEE service. Only after reproducing that data flow on the host should a candidate be accepted: the first decrypted block must satisfy its framing checksum and `UDTRFIRM`/header CRC, and subsequent blocks must satisfy their checksums, lengths, and end flag. Cross-check a second XR2 package before claiming a general decoder. No XR2 plaintext, FDAT key, repacker, camera-menu boot, or flashable image was obtained in this run.
